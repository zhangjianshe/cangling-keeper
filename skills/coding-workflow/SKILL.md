# 编程任务工作流

目标是交付符合用户要求、经过验证的代码，不以工具调用成功或计划完成代替验收。按当前任务选用下面步骤，不需要机械地逐条调用工具。

## 从要求到实现

- 提取公开接口、输入类型和边界、错误返回、数据持久化以及运行方式。保留用户要求的准确名称和签名；不自行替换为近似接口。
- 多步任务用简短计划记录实现、验证和收尾；只有阶段发生变化才更新。将关键要求对应到可执行检查。
- 先完成可调用的最小实现，再增加功能。创建文件直接提交完整内容；不要先用命令创建空文件再反复覆盖。
- 根据已有环境信息选工具，不重复检测。按项目相对路径工作，命令使用当前项目工作目录，不猜绝对路径。

## 根据证据调试

测试失败时先读结构化摘要的异常类型、消息、位置、源码行和失败用例。区分原始异常与由其导致的后续断言失败。

1. 用一句话描述已观察到的事实，不先猜结论。例如“调用处需要某字段，但返回值缺少该字段”。
2. 找到这个值的产生处和使用处，一次读取相关完整函数及必要测试。已有同版本内容时复用，不按小片段逐页浏览。摘要缺少调用链或上下文时才查完整日志。
3. 提出一个可验证原因，核对证据后提交最小修复。读取不能验证该原因时，明确还缺什么信息，再做针对性检查。
4. 修复后运行相关测试，再做完整回归。没有代码或测试环境变化时，不重复相同失败测试。

常用检查方向（不是预设根因）：

- 方法调用要求的类型与实际输入类型是否一致；边界校验是否在转换或调用之前。
- 数据库查询/解析器返回的字段与消费代码读取的字段是否一致；缺字段不等同于整个对象为空。
- 初始化是否发生在请求处理之前；资源是否跨线程使用且符合其生命周期。
- 测试是否独立创建和清理数据；单测成功而整套失败时，检查共享状态和顺序依赖。
- 同源错误是否有多个调用点；证据相同的修改可合并，不能未经核对机械替换。

不要反复解释相同猜测。没有新证据时选择一个动作：补充必要证据、提交有依据的修复，或说明具体阻塞。不要以修改断言、删除测试或弱化需求使失败消失；只有证据表明测试不符合契约时才修正测试，并解释理由。

## 验证与交付

- 使用项目现有测试入口；Python unittest 可使用 run_tests，保留完整结果。不要把读取日志的命令成功当成测试成功。
- 核对测试数量、失败、错误和跳过；零测试、过期结果以及未运行的检查不算通过。
- 对照最初要求，补查未覆盖的输入类型、边界及失败路径。自编测试通过不代表需求全部满足。
- 最后简述实际修改、已执行检查与结果，以及未完成事项。不在预算不足时虚报完成。

技能不授予执行权限。写入、补丁和命令仍走原审批及版本校验；拒绝后不换工具绕过。停止和预算到期时保留现有成果，报告未完成部分，不自行扩大预算。
